21. Final pros and cons
Proposed JWT approach — Pros
1. Minimal UI change
This is the biggest advantage.
JWT can live in:
HttpOnly Secure cookie
and the browser handles it.
2. Centralized validation
Instead of each controller implementing security:
Security Filter
     ↓
JWT validation
3. Stateless
No session database is required for basic validation.
4. Expiration
JWT naturally provides:
iat
exp
5. Token uniqueness
jti provides a unique token identifier and gives you the option of future replay/revocation mechanisms.
6. Can propagate across services
Useful if several CASA services participate in the same journey.
22. Cons / risks
1. Cookie introduces CSRF consideration
Because browsers automatically send cookies.
Mitigate with:
SameSite
Origin
Fetch Metadata
and CSRF tokens if your threat model/flow requires them.
2. JWT revocation is harder
If stolen:
valid signature + valid expiry
means it can potentially be replayed.
If you need immediate revocation, consider:
jti → server-side denylist
or use an opaque server-side session.
3. Key management
You need proper:
signing key
rotation
storage
access control
Don't put the signing secret directly in application configuration/source.
4. Legacy compatibility
Existing integrations may behave differently once cookies/security headers are introduced.
5. IP/fingerprint binding can create false positives
This is why I would leave both out of mandatory validation.
